# M2: BLE Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pull voice notes from the device over BLE without loss, even across link drops, from a Python CLI and from an Android PWA — all verified without the board.

**Architecture:** A Python reference device model generates session transcripts (`protocol/vectors/sync.txt`). A portable C transfer engine replays them byte for byte on the host and is wrapped by a thin NimBLE layer. Python and TypeScript sync clients share one set of rules and are tested against their device models with fault injection; the PWA adds IndexedDB storage, ADPCM playback and a one-screen UI, end-to-end tested with a fake `navigator.bluetooth`.

**Tech Stack:** C11 + CMake/ctest; ESP-IDF 5.4.4 NimBLE; Python >= 3.10 stdlib + optional `bleak>=1.0`; Node 22, Vite 8, TypeScript 5.9, Vitest 5, fake-indexeddb 6, Playwright 1.64.

**Spec:** `docs/superpowers/specs/2026-10-15-m2-ble-sync-design.md` (protocol rules in its section 2 are referenced below as "S2.n").

## Global Constraints

- Wire format is PROTOCOL.md v1; the only reinterpretation is `[0x83][status != 0]` = transfer failed (S2.1).
- DATA payload `mtu - 5`, capped at 507; minimum MTU 64; `battery_pct` 255 = unknown; LIST/`file_count` exclude the note being recorded.
- Credit policy (both clients): GET with `window` credits (default 16); after each `window // 2` chunks consumed, send `CREDIT(window // 2)`.
- Two-phase delete: DELETE only after the verified note is durably stored (`.e32` renamed / IndexedDB `notes` written).
- Note key for clients: `"<file_id>:<boot_id>:<start_us>"`.
- Python tests never import `bleak`; HTTP/BLE never touched in tests.
- All little-endian. Commits end with the branch's attribution trailer. Decisions not in the spec go to `docs/DECISIONS.md`.
- Build firmware locally with: `env -u VIRTUAL_ENV PATH=$HOME/esp/py312-shim:/usr/bin:/bin bash -c '. ~/esp/esp-idf-v5.4.4/export.sh >/dev/null && cd firmware && idf.py build'` (delete `firmware/sdkconfig` after changing `sdkconfig.defaults`).

## Review Focus

1. **Link drops after DELETE is sent but before its ack.** On reconnect the note may or may not still be listed; a note already complete locally under the same key must not be refetched — only DELETE is resent. Test: Task 6 `test_complete_local_note_is_not_refetched_only_deleted`; Task 10 `skips refetch of a note already stored`.
2. **Device NVS erased, so file ids restart.** A new note with an old `file_id` but a different `boot_id`/`start_us` must be stored as a new note, not resumed onto the old one. Test: Task 6 `test_reused_file_id_with_new_header_is_a_new_note`; Task 10 `note key includes boot and start`.
3. **App or CLI killed mid-transfer.** Partial bytes survive and the next sync resumes at their length. Test: Task 6 `test_resume_from_part_file_across_runs`; Task 10 `resumes from persisted segments`.
4. **Phone negotiates MTU < 64 / note busy while recording.** Clear error for MTU without retry loops; a busy note is skipped and the rest syncs. Test: Task 6 `test_mtu_too_small_fails_fast`, `test_busy_note_is_skipped`.
5. **Zero-length note (`empty.e32`, 32 bytes).** Syncs, verifies and decodes to an empty WAV in both clients. Test: every two-note sync test uses `tone_16k.adpcm.e32` as id 1 and `empty.e32` as id 2.

# device_model.py
@dataclass
class DeviceConfig: boot_id: int = 5; fw: tuple[int, int, int] = (0, 2, 0); codecs_mask: int = 3; battery_pct: int = 255; free_bytes: int = 2_500_000; now_us: int = 1_000_000

Line grammar (one directive per line, single spaces, hex lowercase): `SCENARIO <name>`, `CONFIG boot_id=<n> fw=<a.b.c> codecs=<n> battery=<n> free=<n> now_us=<n>`, `FILE <id> <vector filename>`, `BUSY <id> <vector filename>`, `FAILREAD <id> <offset>`, `CONNECT <mtu>`, `MTU <mtu>`, `SEND <hex>`, `INFO`, `DISCONNECT`, `EXPECT CTRL <hex>`, `EXPECT DATA <hex>`, `EXPECT INFO <hex>`, `END`. After `SEND`, `CONNECT` and `MTU` the harness runs until idle; `EXPECT` lines list every output of the preceding action in order.

Scenarios (files are id 1 `tone_16k.adpcm.e32` and id 2 `empty.e32` unless noted; MTU 64 unless noted): `info`, `set_time`, `list_two` (with `BUSY 3 empty.e32`, which must not appear), `list_empty` (no files), `get_full_multi_credit` (id 1, credits 50, then CREDIT 50, CREDIT 50 until done; MTU 247), `get_zero_credits_then_credit`, `get_resume_offset` (offset 1000, credits 4, CREDIT until done), `get_offset_equals_size` (id 2, offset 32), `get_offset_beyond_size`, `get_unknown`, `get_busy`, `get_replaces_active`, `abort_mid_transfer`, `credit_without_transfer`, `delete_ok_then_list`, `delete_unknown`, `delete_busy_recording`, `delete_busy_transferring`, `unknown_opcode`, `bad_length` (GET with 9 arg bytes), `mtu_too_small` (CONNECT 23: LIST → `81 05`; CREDIT → nothing; MTU 64 then LIST works), `disconnect_resume` (GET credits 10 of id 1, DISCONNECT, CONNECT, GET at offset `10*59`), `read_failure` (`FAILREAD 1 2000`, GET credits 100 → chunks up to the failing one, then `83 06`).
